## 157. TLS in Kubernetes

기본 요구 사항: 모든 서비스와 클라이언트 간의 모든 상호 작용은 안전해야 함
1. 클러스터 내의 모든 서비스가 서버 인증서를 사용함
2. 모든 클라이언트가 클라이언트 인증서를 사용하여 본인임을 확인함
TLS 인증서: crt + private key

<br>

Server Certificates
- kube-apiserver: 외부 사용자 및 다른 컴포넌트가 kubernetes 클러스터를 관리하는 데 사용하는 https api endpoint
- etcd server: 클러스터에 대한 모든 정보를 저장
- kubelet server: kube-apiserver이 worker node와 상호 작용하기 위해 통신하는 https api endpoint

<br>

Client Certificate
- admin 사용자가 admin TLS 인증서로 kubectl REST API를 통해 kube-apiserver 접속 시 필요
- kube-apiserver와 클라이언트가 연결될 때 client TLS 인증서 필요
    - kube-scheduler: 스케줄링이 필요한 파드를 찾음
    - kube controller manager
    - kube-proxy
- kube-apiserver와 etcd server이 통신할 때 kube-apiserver의 인증이 필요
- kube-apiserver와 개별 노드의 kubelet server이 통신해 워커 노드를 모니터링하는데, 이때도 TLS 인증서가 필요

<br>
<br>

## 158. TLS in Kubernetes - Certificate Creation

EASYRSA, OpenSSL, CFSSL 등 다양한 도구가 있음

Certificate Authority (CA)
1. `openssl genrsa -out ca.key 2048` 개인 키를 생성함
2. `openssl req -new -key ca.key -subj "/CN=KUBERNETES-CA" -out ca.csr` 인증서 서명 요청 
3. `openssl x509 -req -in ca.csr -signkey ca.key -out ca.crt` 인증서 서명 (자체 서명)

<br>

Admin User Client Certification
1. `openssl genrsa -out admin.key 2048` 개인 키를 생성함
2. `openssl req -new -key admin.key -subj "/CN=kube-admin/OU=system:masters" out admin.csr` 인증서 서명 요청, 해당 이름으로 kube-control client가 인증함
3. `openssl x509 -req -in admin.csr -CA ca.crt -CAkey ca.key -out admin.crt` 인증서 서명, CA 사용
- 인증서에 사용자에 대한 그룹 상세 정보를 추가해 admin과 일반 유저를 구분함
- `curl https://kube-apiserver:6443/api/v1/pods --key admin.key --cert admin.crt --cacert ca.crt` 명령어처럼 사용 가능
- 혹은 이런 모든 매개변수를 kube config 구성 파일로 이동해 server API endpoint, 사용할 인증서 등을 지정함
- kube scheduler의 경우 쿠버네티스 컨트롤 플레인의 시스템 구성 요소이므로 이름 앞에 `SYSTEM:` prefix를 붙여야 함
- 인증서가 있는 서버 도는 클라이언트를 구성할 때마다 CA 루트 인증서도 함께 지정해야 함

<br>

Server Side Certification (etcd)
- 여러 서버에 걸쳐 클러스터로 배포하는 경우 구성원 간의 통신 보호를 위한 peer 인증서가 필요함
- 모든 작업이 kube-apiserver를 통해 이루어지기 때문에 클러스터 내에서 다양한 이름과 별칭으로 불림 → kubernetes, kubernetes.default 등
- IP 주소 및 kube-apiserver를 실행하는 호스트의 IP 주소가 인증서에 포함되어야 함
1. `openssl genrsa -out apiserver.key 2048` 개인 키를 생성함
2. openssl.cnf 파일에 kube-apiserver이 사용하는 모든 DNS와 IP 주소를 작성함
3. `openssl req -new -key apiserver.key -subj "/CN=kube-apiserver" out apiserver.csr -config openssl.cnf` 인증서 서명 요청
4. `openssl x509 -req -in apiserver.csr -CA ca.crt -CAkey ca.key CAcreateserial -out apiserver.crt -extensions v3_req -extfile openssl.cnf -days 1000` 인증서 서명
- 인증서의 위치는 ExecStart에서 확인할 수 있음

<br>

kubelet server의 경우 kube-apiserver이 노드를 모니터링하고 노드에서 예약할 파드에 관한 정보를 전달하기 위해 통신함<br>
따라서 클러스터의 각 노드에 대해 키 인증서 쌍이 필요한데, 인증서의 이름은 노드의 이름을 따서 생성되고 kubelet-config.yaml에서 사용됨<br>
또한 kubelet이 kube-apiserver와 통신을 위해 인증하는데 사용되는 클라이언트 인증서 세트도 system:node:<노드이름>으로 생성하고, 적절한 권한을 가지고 있는지 검토하기 위해 system:node 그룹에 추가해야 함

<br>

## 159. View Certificate Details

kubernetes 클러스터를 처음부터 배포하는 경우, 모든 인증서를 직접 생성함<br>
혹은 kubeadm과 같은 자동화된 프로비저닝 도구를 사용하는 경우, 모든 구성 요소를 노드에 네이티브 서버로 배포함<br>
[스프레드시트](/esc/2026-02-04/kubernetes-certs-checker.xlsx)를 활용해 사용된 인증서 파일, 경로, 구성된 이름, 구성된 대체 이름, 인증서 계정이 속한 조직, 만료일을 확인해야 함

`cat /etc/kubernetes/manifests/kube-apiserver.yaml`명령어로 서버가 사용하는 모든 인증서에 대한 정보를 확인해 각 용도에 사용되는 인증서 파일을 식별해 기록함<br>
그런 다음, 각 인증서를 가져와서 내부를 살펴보고 해당 인증서에 대한 자세한 정보를 찾음<br>
`openssl x509 -in /etc/kubernetes/pki/apiserver.crt -text -noout`처럼 인증서를 디코딩하고 세부 정보를 확인함<br>
문제가 발생하는 경우 `journalctl -u etcd.server -l` 혹은 `kubectl logs etcd-master` 명령어로 로그를 살펴보는 것을 추천함<br>
핵심 구성 요소가 다운되는 경우 kubectl이 동작하지 않으므로 `crictl ps -a` 명령으로 모든 컨테이너를 나열한 다음 `crictl logs <containerID>`로 로그를 확인해야 함

<br>
