## 10. ETCD For Beginners

관계형 데이터베이스
- 새로운 정보를 추가해야 할 때마다 테이블 전체가 영향을 받아 빈 셀이 많이 생김
- 스키마가 엄격하고 SQL을 사용하여 복잡한 쿼리를 수행할 수 있어 성능이 좋음
- 유연성 측면에서 매우 경직되어 있으며 정형 데이터에 가장 적합함

<br>

Document Store
- 개인에 대한 정보를 문서 형태로 저장함 (일반적으로 json 형식)
- 파일은 어떤 형식이나 구조로든 존재할 수 있으며, 한 파일을 변경해도 다른 파일에는 영향 X
- 서로 다른 테이블을 조인하여 복잡한 쿼리를 조인하는 데 제한이 있지만 문서 구조 덕분에 매우 우연하게 사용 가능함

<br>

키-값 저장소
- 키에 대한 값을 저장함, 값은 property 집합일 수도 있고 전체 json 문서 자체일 수도 있음
- 스키마가 필요하지 않으며 복잡한 쿼리 지원 X
- 성능이 매우 빠르고 유연성이 뛰어나 데이터 구조에 대한 걱정 없이 저장 가능함

<br>

**etcd**: 신뢰할 수 있는 분산형 키-값 저장소
- etcd를 실행하면 기본적으로 포트 2379에서 수신 대기하는 서비스(= 서버)가 시작됨
- etcd는 시스템 서비스 또는 K8S 클러스터의 파드로 실행하는 것이 가장 이상적임
- 클라이언트를 etcd 서비스에 연결하고, etcdctl 커맨드를 이용해 정보를 저장하고 검색 가능함
- 정식 버전으로는 v2.0, 최적화가 이루어진 v3.n이 있으며 두 버전은 명령어 호환이 거의 되지 않으니 주의 필요

<br>

## 11. ETCD in Kubernetes

etcd 데이터 저장소에는 node, pod, config, secret, account, role, binding 등과 같은 정보가 저장되고 kubectl get 명령을 실행할 때 표시되는 etcd 서버에서 정보를 가져옴<br>
노드 추가, 파드 배포, replicaset 등과 같은 클러스터 변경 사항은 etcd 서버에서 업데이트 된 후에만 데이터의 업데이트를 허용하여 데이터 일관성을 보장하고 클러스터 내의 모든 인스턴스가 동일한 상태를 유지하도록 함.

클러스터를 처음부터 설정하는 경우 etcd 바이너리를 직접 다운로드 → 바이너리 설치 → 마스터 노드에서 etcd를 서비스로 구성하여 배포하는 단계를 거침<br>
서비스에는 etcd를 클러스터로 구성하는 방법과 TLS 인증서에 대한 내용이 포함됨<br>
etcd.service에서 --advertise-client-urls는 etcd가 수신하는 주소이며, 기본값으로 `https://${INTERNAL_IP}:2379`가 지정되어 있음. etcd 서버에 접속하고 싶다면 kubeAPI 서버에서 해당 URL을 구성해야 함

kubeadm을 사용해 클러스터를 설정하는 경우 etcd 서버가 kube-system namespace에 pod로 배포함<br>
이 포드 내의 etcd-master 유틸리티를 사용해 etcd db를 탐색 가능함<br>
etcd의 root 경로는 registry이며 그 아래에 minions, pods, replicasets, deployments 등의 값을 저장함<br>
고가용성 환경에서는 클러스터에 여러 개의 마스터 노드를 보유하게 되는데, 이 경우 etcd 서비스 구성에서 올바른 매개변수를 설정하여 etcd 인스턴스가 서로에 대해 알 수 있어야 함<br>
--initial-cluster에서 etcd 서비스의 여러 인스턴스를 지정할 수 있음

<br>

## 13. kube-API server

kube-apiserver: 쿠버네티스의 기본 관리 컴포넌트, etcd 데이터 저장소와 직접 상호작용하는 유일한 구성 요소<br>
kube control에서 pod 생성 명령을 실행하면 다음 과정이 진행됨:
1. 유저 인증 및 요청 검증
2. Pod 객체 생성
3. etcd 서버 정보 업데이트
4. API Server에서 할당되지 않은 신규 Pods를 모니터링해 적합한 노드를 찾아 APi Server에 통신
5. 지정된 워커 노드의 kubelet은 Pod를 생성하고 컨테이너 런타임 엔진에 애플리케이션 이미지 배포
6. 배포가 완료되면 kubelet이 API Server 업데이트 → API Server가 etcd 클러스터에 내용 반영

<br>

k8s 아키텍처는 다양한 방식으로 서로 통신하며 작동하는 수많은 구성 요소들로 이루어지기 때문에 다른 구성 요소의 위치를 모두 알아야 함<br>
인증, 권한 부여, 암호화, 보안 모드가 다양해 선택의 폭이 넓으며 kube-apiserver의 설정 중 상당수가 인증서임<br>
--etcd-server는 etcd 서버의 위치를 지정하는 옵션으로, kube-apiserver가 etcd 서버에 연결하는 방식임

kubeadm으로 설정하는 경우 master 노드의 kube-system namespace에서 kube-apiserver-master를 파드로 배포함<br>
kubeadm이 아닌 경우 /etc/kubernetes/manifests/kube-apiserver.yaml에서 설정을 확인할 수 있음<br>
혹은 ps -aux | grep kube-apiserver 명령어로 kube-apiserver에서 적용된 옵션을 확인할 수도 있음

<br>

## 14. Kube Controller Manager

kube controller-manager: 시스템 내의 다양한 구성 요소의 상태를 지속적으로 모니터링하고 전체 시스템을 원하는 작동 상태로 만들기 위해 작동하는 프로세스, k8s의 다양한 컨트롤러를 관리함

node-controller: node의 상태를 모니터링하고 애플리케이션이 계속 실행되도록 필요한 조치를 취함 - kube-apiserver<br>
5초마다 노드의 상태를 확인해 모니터링하며 노드로부터 수신을 중단하면 40초 동안 기다렸다가 해당 노드는 연결할 수 없는 것으로 표시됨<br>
노드가 연결할 수 없는 것으로 표시되면 5분 동안 다시 연결할 수 있는 시간이 주어지고, 그 뒤 해당 노드에 할당된 파드를 제거하고 정상 노드에 프로비저닝함

replication-controller: pod가 replicaset의 일부인 경우 사용됨<br>
replicaset의 상태를 모니털이하고 파드가 죽으면 다른 파드를 생성해 세트 내에서 원하는 수의 파드를 항상 사용할 수 있는지 확인함

이외에도 쿠버네티스의 모든 요소에 대해 컨트롤러가 존재하며, kube-controller-manager라는 단일 프로세스에 패키징되어 있음<br>
노드 모니터 기간, 유예 시간, 타임아웃 시간 등 노드 컨트롤러의 기본 설정은 kube-controller-manager의 옵션으로 작성되어 있으며 수정 가능함<br>
기본적으로 모든 컨트롤러가 활성화되어 있지만 일부 기능만 활성화하도록 선택 가능함

kubeadm으로 설정하는 경우 master 노드의 kube-system namespace에서 kube-controller-manager를 파드로 배포함<br>
kubeadm이 아닌 경우 /etc/kubernetes/manifests/kube-controller-manager.yaml에서 설정을 확인할 수 있음<br>
혹은 ps -aux | grep kube-controller-manager 명령어로 kube-controller-manager에서 적용된 옵션을 확인할 수도 있음

<br>

## 15. Kube Scheduler

kubernetes scheduler는 파드와 노드의 스케줄링을 담당함<br>
어느 노드에 어떤 파드를 배치할지 결정하는 역할만 담당하며, 실제로 노드에 파드를 배치하지는 않음 (노드에 파드를 배치하는 작업은 kubelet이 함)<br>
스케줄러는 각 파드를 살펴보고 (1) 기준이 되지 못하는 노드는 제외하고 (2) 우선순위 함수를 사용해 점수가 높은 노드 배치하며 이 기준에는 CPU 및 메모리 요구 사항, 파드 배치 후 사용 가능한 리소스 양이 될 수 있음

kubeadm으로 설정하는 경우 master 노드의 kube-system namespace에서 kube-scheduler를 파드로 배포함<br>
kubeadm이 아닌 경우 /etc/kubernetes/manifests/kube-scheduler.yaml에서 설정을 확인할 수 있음

<br>

## 16. Kubelet

워커 노드의 kubelet은 노드를 쿠버네티스 클러스터에 등록하고 노드에서 컨테이너 또는 파드를 로드하라는 지시를 받으면 컨테이너 런타임 엔진에 필요한 이미지를 가져와 인스턴스를 실행하도록 요청함<br>
그 뒤 kubelet은 파드와 그 안에 있는 컨테이너의 상태를 계속 모니터링하고 적시에 kube-apiserver에 보고함

kubeadm으로 설정하는 경우 자동으로 배포되지 않고 워커 노드에 수동으로 설치해야 함<br>
ps -aux | grep kubelet 명령어로 실행 중인 kubelet 프로세스와 옵션을 확인할 수 있음

<br>

## 17. Kube Proxy

클러스터에 파드 네트워킹 솔루션을 배포하여 포드와 포드를 통신할 수 있음<br>
파드 네트워크는 모든 파드가 연결되는 클러스터의 모든 노드에 걸쳐 있는 내부 가상 네트워크이며, 이 네트워크를 통해 서로 소통할 수 있음

첫 번째 노드에는 웹 애플리케이션이 배포되어 있고, 두 번째 노드에는 데이터베이스 애플리케이션이 배포되어 있다고 가정해보자.<br>
웹앱은 단순히 파드의 IP에 연결할 수 있지만, 데이터베이스 파드의 IP가 항상 동일하게 유지된다는 보장은 없으므로 웹앱이 데이터베이스에 액세스하는 데 서비스를 사용하는 것이 더 좋음<br>
따라서 클러스터 전체에 데이터베이스 애플리케이션을 노출하는 서비스를 생성해 웹 애플리케이션은 서비스 DB의 이름을 사용해 데이터베이스에 액세스할 수 있음<br>
또한 이 서비스는 파드가 IP 또는 이름을 사용해 서비스에 접속하려고 할 때마다 할당된 IP 주소를 가져와 트래픽을 백엔드(이 경우 데이터베이스)로 전달함

서비스는 쿠버네티스 메모리에만 존재하는 가상 구성 요소로, 파드와 같은 컨테이너가 아니므로 인터페이스나 능동적 수신 프로세스가 없어 파드 네트워크에 참여할 수 없음<br>
kube-proxy는 쿠버네티스 클러스터의 각 노드에서 실행되는 프로세스이고 새로운 서비스를 찾아 각 노드에 적절한 규칙을 생성해 서비스로의 트래픽을 백엔드 포드로 전달함<br>
이를 수행하는 방법 중 하나는 iptables 규칙을 사용하는 것으로, 클러스터의 각 노드에서 서비스의 IP(10)으로 향하는 트래픽을 포워딩하는 iptables 규칙을 생성함

kubeadm의 경우 각 노드에 kube-proxy를 파드로 배포함. 실제로 daemonset으로 배포되므로 클러스터의 각 노드에는 항상 단일 파드가 배포됨
