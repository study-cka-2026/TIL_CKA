## 78. Multiple Schedulers

자체적인 쿠버네티스 스케줄러 프로그램을 작성하고 패키징하여 기본 스케줄러 혹은 추가 스케줄러로 배포 가능함<br>
쿠버네티스 클러스터는 한 번에 여러 개의 스케줄러를 가질 수 있는데, 파드를 배포할 때 이를 지정할 수 있음<br>
이름을 지정하지 않으면 기본 스케줄러로 설정됨<br>
kubeadm 배포를 사용하면 모든 컨트롤 플레인 요소가 쿠버네티스 클러스터 내에서 파드 또는 deployment로 실행되기 때문에 일반적인 경우 수동 배포 X

[scheduler-config.yaml](/esc/2026-01-17/scheduler-config.yaml)의 leadershipElection 옵션은 여러 마스터 노드에서 스케줄러 프로세스가 실행되는 경우, 해당 옵션이 true인 스케줄러가 적용됨<br>
[Configure Multiple Schedulers](https://kubernetes.io/docs/tasks/extend-kubernetes/configure-multiple-schedulers/)에서 추가 yaml 내용 확인 가능<br>
스케줄러를 Deployment 방식으로 배포하기 위해서는 권한 부여와 configmap 생성이 필요함<br>
파드로 배포하는 경우 kube-system namespace의 파드를 확인할 수 있음<br>
파드의 스케줄러는 `kubectl get events -o wide` 명령어 중 예약된 이벤트를 통해 확인할 수 있음

## 81. Configuring Scheduler Profiles

1. 파드 생성 후 스케줄링 대기열에 포함됨 - 파드에 정의된 우선순위에 따라 정렬됨: PrioritySort
2. 파드를 실행할 수 없는(= 충분한 자원이 없는) 노드 필터링: NodeResourcesFit, Nodename, NodeUnschedulable
3. 리소스 사용 후 확보할 여유 공간에 따라 노드에 점수 할당: NodeResourcesFit, ImageLocality
4. 최종적으로 가장 높은 점수를 받은 노드에 파드가 바인딩: DefaultBinder

이 과정의 Plugin와 파드를 extension point로 연결된다.

여러 개의 스케줄러는 별도의 프로세스이기 때문에 유지 관리하는 데 추가적인 노력이 필요하고, 스케줄링 결정을 내리는 데 경쟁 조건에 부딫힐 수 있음<br>
쿠버네티스에서는 단일 스케줄러에서 여러 프로필을 지원하는 기능이 도입되어 각 프로필에 대해 별도의 스케줄러 이름을 지정할 수 있음<br>
각 스케줄러에 대해 별도의 프로필이 생성되어 각 스케줄러 자체가 별도의 스케줄러로 작동하지만, 각 스케줄러가 동일한 바이너리에서 실행된다는 점을 제외하면 동일함<br>
서로 다른 프로필 스케줄러가 다르게 작동하려면 원하는 방식으로 스케줄러를 설정(Taint, Toleration, Plugin 지정)하여 구성함

## 83. Admission Controllers

쿠버네티스에 요청 전송(kubelet) → kube-apiserver로 전달 → Authentication → Authorization → Admission Controllers → 요청 실행 → etcd 데이터베이스에 유지
요청이 apiserver에 도착하면 인증 프로세스를 거치는데, 일반적으로 인증은 인증서를 통해 이루어짐
요청이 kubectl을 통해 전송된 경우, ~/.kube/config 파일에 인증서가 구성되고, 인증 프로세스는 요청을 전송한 사용자를 식별하고 사용자가 유효한지 확인함
그 후 사용자에게 해당 작업을 수행할 수 있는 권한이 있는지 확인([Role-based access control](/esc/2026-01-17/developer-role.yaml))하고 허용되면 요청이 실행됨

특정 내부 레지스트리의 이미지만 허용하거나 최신 태그의 이미지만 사용하거나, root 유저는 사용하지 않는 등의 추가 권한 제어는 RBAC로는 달성할 수 없음
따라서 **Admission Controllers(권한 클러스터)**를 사용하여 이미지 출처 검증, 특정 구성 보장 등의 정책을 시행할 수 있음
- AlwaysPullImages: 파드가 생성될 때마다 이미지 pull
- DefaultStorageClass: Persist Volume Claims(PVC)에 기본 스토리지 클래스를 자동으로 할당함
- EventRateLimit: API 서버가 동시에 처리할 수 있는 요청의 수 제한
- NamespaceExists: 존재하지 않는 namespace에 대한 요청 거부
- NamespaceAutoProvision - Namespace Lifecycle admission으로 대체

활성화된 admission controllers는 `kubectl exec kube-apiserver-controlplane -n kube-system -- kube-apiserver -h | grep enable-admission-plugins` 명령어로 찾아볼 수 있음
추가로 활성화하고 싶다면 /etc/kubernetes/manifests/kube-apiserver.yaml 파일에서 command에 `--enabel-admission-plugins=<추가>`

## 86. Validating and Mutating Admission Controllers

Mutating Admission Controllers는 객체가 생성되기 전에 객체 자체를 변경하거나 변형할 수 있음
Validating Admission Controllers는 객체의 유효성을 검사하여 허용 또는 거부할 수 있는 컨트롤러임
또는 요청 변경(Mutating)과 요청 검증(Validating)의 두 가지 기능을 모두 수행할 수 있는 Admission Controllers가 있을 수 있음
일반적으로는 Mutating Admission Controllers가 먼저 호출되고 Validating Admission Controllers의 유효성을 검사하는데, 이는 Mutating에서 변경한 모든 사항을 Validating 과정에서 고려하기 위함임

자체적인 Admission Controller를 만들기 위해서는 MutatingAdmissionWebhook과 ValidationAdmissionWebhook을 사용함
웹훅이 Kubernetes 클러스터 내부 또는 외부에서 호스팅되는 서버를 가리키도록 구성하고 서버에는 자체 AdmissionWebhook을 실행해 요청이 자체 AdmissionController를 통과하면 구성된 Webhook에 도달함
Webhook에서는 json 형식의 Admission Webhook Server를 호출해 요청 허용 여부를 포함한 Admission Review Object를 응답해 요청을 허용/거부함

1. 자체 로직이 있는 Admission Webhook Server 배포 - 변경 및 유효성 검사 API를 수락해 지정된 json 객체로 응답
2. Webhook Server 호스팅 - 서버 실행 혹은 컨테이너화하여 Kubernetes Cluster에 Deploy로 배포(webhook-service 필요)
3. 서비스에 연결하고 요청의 유효성을 검사하거나 변경하도록 [클러스터 구성](/esc/2026-01-17/valication-webhook.yaml)
