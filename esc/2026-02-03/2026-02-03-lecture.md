## 152. Kubernetes Security Primitives (보안 매개변수)

호스트에 대한 모든 액세스는 보안 루트 액세스를 비활성화하고, 비밀번호 기반 인증을 비활성화하고, SSH 키 기반 인증만 사용할 수 있도록 설정해야 함

**API 서버 자체에 대한 액세스 제어**
- kube-apiserver는 kubernetes 내 모든 작업의 중심이며 kubectl 또는 API에 직접 액세스하여 거의 대부분의 작업을 상호 작용함
- API 서버에 액세스할 수 있는 사람은 인증 매커니증에 의해 정의됨 - Service 계정 생성 등
- API 서버에 액세스하는 사람은 권한 부여 매커니즘에 따라 수행할 수 있는 작업이 정의됨
    - 역할 기반 액세스 제어
    - 속성 기반 액세스 제어 노드, 권한 부여자, 웹훅 등 다른 권한 부여 모듈도 있음
- etcd, kube controller-manager, kube-scheduler, kube-proxy, kubelet 등 구성 요소 간의 모든 통신은 TLS 암호화를 사용함
- 기본적으로 모든 파드는 클러스터 내의 다른 파드에 액세스할 수 있으며 네트워크 정책으로 액세스를 제한할 수 있음

## 153. Authentication

Authenticatoin(인증) 매커니즘을 통해 Kubernetes 클러스터에 대한 액세스를 보호할 수 있음

관리 목적으로 Kubernetes 클러스터에 액세스하는 사용자는 어떻게 나눌 수 있을까?
- 사용자: Admin, Developers
- 서비스: Bot, Service, Aplication

kubernetes는 기본적으로 사용자 계정을 관리하지 않고, 사용자 세부 정보 또는 인증서가 포함된 파일 등에 의존함<br>
서비스 계정의 경우 kubernets가 관리함<br>
사용자 액세스는 kube-apiserver에서 진행됨. 모든 요청은 kube-apiserver를 통해 이루어지기 때문임

kube-apiserver는 요청을 처리하기 전에 정적 토큰 파일이나 인증서, 인증 프로토콜을 통해 요청을 인증함<br>
static token file 방식은 사용자 세부 정보가 포함된 csv 파일에 그룹과 토큰을 작성하고 토큰 파일을 kube-apiserver에 전달해 인증하는 동안 토큰을 bearer 토큰으로 지정함<br>
하지만 해당 방식은 안전하지 않으므로 권장되지 않지만 가장 쉬운 방식임

## 156. TLS Basics

인증서는 거래 중 두 당사자 간의 신뢰를 보장하는 데 사용됨 <br>
ex) 사용자가 웹 서버에 액세스할 때 사용자와 서버 간의 통신 암호화 및 실제 서버임을 보증함

- 대칭 암호화
    - 데이터가 키를 이용하여 암호화되고, 암호화 키의 사본을 함께 전달함
    - 데이터를 암호화하고 해독하는 데 동일한 키를 사용하고, 발신자와 수신자 간에 키를 교환해야 하기 때문에 보안에 취약함
- 비대칭 암호화
    - 개인 키와 공개 키라는 한 쌍의 키를 사용함, private key는 나만 가지고 있고, public lock은 모두가 접근할 수 있음
    - public lock을 이용해서 암호화를 한 뒤 private key로 복호화함 → key를 가지고 있는 나만 복호화 가능
    - SSH 접속: `ssh-keygen`으로 public lock와 private key를 생성해 public lock을 이용해 서버를 암호화하면 private key를 가지고 있는 사람만 접속 가능함

1. 비대칭 암호화로 서버에 공개 키를 가지고 있는 상태에서 사용자가 https로 접속하면 공개키를 전달함
2. 사용자의 브라우저는 서버에서 제공한 공개키를 사용하여 대칭 키를 암호화함
3. 암호화된 대칭 키를 서버에 전달함
4. 서버는 개인 키를 이용해 메시지를 해독하고 대칭 키를 획득함
5. 대칭 키는 사용자와 서버만 사용할 수 있으므로 서버와 사용자는 대칭 키를 사용해 데이터를 암호화하고 전송할 수 있음

<br>

해커가 웹사이트를 복제한 뒤 네트워크 라우팅을 복제 웹사이트로 연결하면 사용자가 암호화된 대칭 키를 해커에게 보내고, 이것을 복호화해 대칭 키를 얻을 수 있음<br>
따라서 인증서 발급자, 공개, 서버 키, 서버 위치 등이 작성된 인증서를 함께 전달해 웹 서버의 신원을 확인함<br>
인증 기관(CA)가 서명한 인증서의 경우에만 인증서 유효성 검사를 통과할 수 있음<br>
합법적인 인증 기관은 개인 키를 사용해 인증서에 서명하고, 공개 키는 브라우저에 내장되어 있으므로 합법적인 인증 기관임을 확인 가능함<br>
조직 내에서 비공개적으로 호스팅되는 서버의 경우 비공개 CAS를 호스팅해 사용할 수 있음<br>
클라이언트는 유효한 CA에서 키 쌍과 서명된 인증서를 생성하고, 인증서를 서버로 전송하여 클라이언트가 해당 유저임을 인증함<br>
이 전체 인프라를 **공개 키 인프라(PKI)**라고 함
