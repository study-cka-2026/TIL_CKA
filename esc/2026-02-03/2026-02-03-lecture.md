## 152. Kubernetes Security Primitives (보안 매개변수)

호스트에 대한 모든 액세스는 보안 루트 액세스를 비활성화하고, 비밀번호 기반 인증을 비활성화하고, SSH 키 기반 인증만 사용할 수 있도록 설정해야 함

**API 서버 자체에 대한 액세스 제어**
- kube-apiserver는 kubernetes 내 모든 작업의 중심이며 kubectl 또는 API에 직접 액세스하여 거의 대부분의 작업을 상호 작용함
- API 서버에 액세스할 수 있는 사람은 인증 매커니증에 의해 정의됨 - Service 계정 생성 등
- API 서버에 액세스하는 사람은 권한 부여 매커니즘에 따라 수행할 수 있는 작업이 정의됨
    - 역할 기반 액세스 제어
    - 속성 기반 액세스 제어 노드, 권한 부여자, 웹훅 등 다른 권한 부여 모듈도 있음
- etcd, kube controller-manager, kube-scheduler, kube-proxy, kubelet 등 구성 요소 간의 모든 통신은 TLS 암호화를 사용함
- 기본적으로 모든 파드는 클러스터 내의 다른 파드에 액세스할 수 있으며 네트워크 정책으로 액세스를 제한할 수 있음

## 153. Authentication

Authenticatoin(인증) 매커니즘을 통해 Kubernetes 클러스터에 대한 액세스를 보호할 수 있음

관리 목적으로 Kubernetes 클러스터에 액세스하는 사용자는 어떻게 나눌 수 있을까?
- 사용자: Admin, Developers
- 서비스: Bot, Service, Aplication

kubernetes는 기본적으로 사용자 계정을 관리하지 않고, 사용자 세부 정보 또는 인증서가 포함된 파일 등에 의존함<br>
서비스 계정의 경우 kubernets가 관리함<br>
사용자 액세스는 kube-apiserver에서 진행됨. 모든 요청은 kube-apiserver를 통해 이루어지기 때문임

kube-apiserver는 요청을 처리하기 전에 정적 토큰 파일이나 인증서, 인증 프로토콜을 통해 요청을 인증함<br>
static token file 방식은 사용자 세부 정보가 포함된 csv 파일에 그룹과 토큰을 작성하고 토큰 파일을 kube-apiserver에 전달해 인증하는 동안 토큰을 bearer 토큰으로 지정함<br>
하지만 해당 방식은 안전하지 않으므로 권장되지 않지만 가장 쉬운 방식임
