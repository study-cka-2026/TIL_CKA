## 7. Cluster Architecture

kubernetes의 목적: 애플리케이션을 컨테이너 형태로 자동화된 방식으로 호스팅하여 필요한 만큼 애플리케이션의 인스턴스를 쉽게 배포하고 애플리케이션 내의 여러 서비스 간에 쉽게 통신할 수 있도록 하는 것

- kubernetes 클러스터: 컨테이너 형태로 애플리케이션을 호스팅하는 물리적 또는 가상, 온프레미스 또는 클라우드에 있는 노드 집합으로 구성됨
- 마스터 노드: 쿠버네티스 클러스터를 관리하고, 여러 노드에 관한 정보를 저장하고, 어떤 컨테이너가 어디로 이동할지 계획하고, 노드와 컨테이너를 모니터링하는 등의 작업 담당
    - **컨트롤 플레인 컴포넌트**라는 일련의 컴포넌트를 사용하여 해당 작업들을 수행함
    - etcd: 컨테이너의 정보 등을 저장하는 고가용성 키-값 저장소
    - kube-scheduler: 컨테이너 리소스 요구 사항, 워커 노드 용향, 노드 선호도 규칙 같은 기타 정책이나 제약 조건에 따라 컨테이너를 배치할 올바른 노드 식별
    - node-controller: 노드 관리, 클러스터에 새 노드를 온보딩하고 노드가 사용 불가가 되거나 파괴되는 상황을 처리
        - replicaton-controller: 복제 그룹에서 원하는 수의 컨테이너가 항상 실행되도록 보장함
    - kube-apiserver: 쿠버네티스의 기본 관리 구성 요소, 클러스터 내의 모든 작업을 오케스트레이션하는 역할, kubernetes api와 클러스터의 상태를 모니터링하고 워커 노드가 서버와 통신하는데 필요한 변경을 수행하는 등 다양한 컨트롤러를 노출함
- 워커 노드: 컨테이너 형태로 애플리케이션이 실행되는 공간
    - 컨테이너 런타임 엔진: 컨테이너를 실행할 수 있는 소프트웨어, kubernetes는 모든 작업이 컨테이너 단위로 이루어지므로 필수적임, 마스터 노드를 포함하여 클러스터의 모든 노드에 Docker 또는 containerd와 같은 이와 동등한 기능을 지원하는 노드가 설치되어 있어야 함
    - kubelet: 클러스터의 각 노드에서 실행되는 에이전트, kube-apiserver의 지시를 수신하고 필요에 따라 노드에 컨테이너를 배포하거나 삭제함
    - kube-proxy: 워커 노드에서 실행 중인 컨테이너가 서로 연결될 수 있도록 필요한 규칙이 워커 노드에 적용되도록 함

## 8. Docker vs ContainerD

Docker의 사용자 경험이 컨테이너 작업을 매우 간단하게 만들었고, 그 결과 Docker는 가장 지배적인 컨테이너 도구가 되었다. 그리고 Kubernetes는 처음부터 Docker를 오케스트레이션하도록 구축했다.

컨테이너 오케스트러이터로서 Kubernetes가 인기를 얻게 되었다. 따라서 rkt과 같은 다른 컨테이너 런타임도 Kubernetes에서 오케스트레이션 되기를 원했다. 그래서 kubernetes는 모든 벤더가 OCI 표준을 준수하는 한 Kubernetes의 컨테이너 런타임으로 작동할 수 있도록 Container Runtime Interface(CRI)를 허용했다. OCI란 Open Container Initiave의 약자로, 이미지 사양과 런타임 사양으로 구성된다. 이미지 사양이란 이미지를 빌드하는 방법에 대한 사양을 정의하고, 런타임 사양은 컨테이너 런타임을 개발하는 방법에 대한 표준을 정의한다.

하지만 Docker는 CRI가 도입되기 전에 구축되었기 때문에 CRI 표준을 지원하지 않았다. 따라서 Kubernetes는 CRI 외부에서 도커를 계속 지원하기 위한 임시적인 방법으로 dockershim을 도입했다. 따라서 대부분의 컨테이너 런타임은 CRI를 통해 작동했지만, Docker는 CRI 없이도 계속 작동할 수 있었다.

Docker는 Docker CLI, Docker API 등 여러 도구로 구성되어 있다. 그리고 컨테이너 런타임인 runc와 runc를 관리하는 daemon인 containerd가 포함되어 있다. 따라서 containerd는 CRI와 호환되며 kubernetes에서 직접 작동할 수 있다. 이는 containerd가 docker와 별도로 독립적인 런타임으로 사용할 수 있다는 의미이다.

kubernetes는 dockershim을 유지 관리하는 것은 불필요한 수고와 복잡성을 더하는 일이었으므로 v1.24 release에서 dockershim을 완전히 제거하여 docker에 대한 지원이 제거되었다. 하지만 이전에 구축된 Docker 이미지는 OCI 표준의 이미지 사양을 따르기 때문에 계속 작동한다. Docker는 containerd와 계속 협력하고 이미지 표준을 따르기 때문에 작동은 가능하지만 Docker 자체는 kubernetes에서 지원하는 런타임에서 제거되었다.

containerd는 docker의 일부이긴 하지만 지금은 독립된 별도의 프로젝트이다. Docker를 직접 설치할 필요 없이 containerd를 자체적으로 설치할 수 있다. docker가 설치되어 있지 않은 경우 containerd만으로 컨테이너를 실행하려면 ctr이라는 컨테이너 디버깅 전용 툴을 사용하면 된다. 하지만 제한된 기능만 지원하기 때문에 사용자 친화적이지 않으므로 프로덕션 환경에서 컨테이너를 실행하거나 관리하는데 사용하기에는 적합하지 않다. 그래서 nerdctl를 많이 사용한다. nerdctl은 docker가 지원하는 옵션의 대부분을 지원하며 containerd에 구현된 최신 기능에 액세스할 수 있다.

crictl은 CRI 호환 컨테이너 런타임과 상호작용하는데 사용되는 명령줄 유틸리티이다. Kubernetes 커뮤니티에서 개발하고 유지 관리중이며 모든 컨테이너 런타임에서 작동한다. nerdctl은 containerd를 위해 구축되었다면 crictl은 다양한 컨테이너 런타임에서 작동하는 kubernetes 관점의 도구라는 점에서 차이점이 있다. 별도 설치가 필요하며 컨테이너 런타임을 검사하고 디버깅하는데 사용된다. kubelet은 한 번에 노드에서 특정 수의 컨테이너 또는 파드를 사용할 수 있는지 확인하는 역할을 담당하는데, crictl을 통해 컨테이너를 생성하려고 하면 kubelet이 생성된 컨테이너를 삭제하게 되므로 crictl을 이용해 kubernetes를 사용하는 것은 권장하지 않는다. crictl은 모든 cri 호환 런타임에 연결하는 데 사용할 수 있으므로 구성했다면 올바른 엔드포인트를 설정해야 한다. 아무것도 구성하지 않은 경우 dockershim > containerd > cri-o > cri-dockerd 순서로 연결된다.

- containerd - ctr : 디버깅 목적으로 사용됨, 사용하지 않는 것을 권장
- containerd - nerdctl: 컨테이너를 생성하는 일반적인 용도로 사용되며 docker cli와 동일하거나 더 많은 기능 지원
- kubernetes - crictl: 모든 cri 지원 런타임에 사용 가능, 디버깅 목적으로 사용됨

## 9. A note on Docker deprecation

Docker는 Kubernetes의 최초이자 유일하게 지원되는 컨테이너 런타임이었으며, 다른 런타임에 대한 개방성을 높이기 위해 CRI가 도입되었다. Docker는 이미지를 빌드하는 데 도움이 되는 빌드 도구인 Docker CLI, API 등 여러 도구가 결합된 형태로 구성되어 있으며, runc라는 컨테이너 런타임과 runc를 관리하는 containerd라는 daemon도 지원했다. 따라서 containerd는 CRI와 호환되며 사용할 수 있으며, Docker와는 별도로 독립적인 런타임으로 사용할 수 있다.

Docker가 지원하는 Docker CLI, API, 빌드, 볼륨 등은 모두 kubernetes 자체에서 처리하기 때문에 Docker 지원을 중단했다. 그렇다고 해서 Docker가 완전히 사라진 것은 아니다. 여전히 가장 인기 있는 컨테이너 솔루션이며 많은 사람들이 일상적인 개발 및 빌드 프로세스에서 사용하고 있다. 다만 kubernetes가 더 이상 런타임으로 Docker를 필요로 하지 않는 것이다. docker가 설치되어 있지 않다면 대부분의 명령어를 nerdctl로 변경하여 사용하면 된다.
