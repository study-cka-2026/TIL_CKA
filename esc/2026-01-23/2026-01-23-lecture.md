## 126. Introduction to Autoscaling

서버 확장 방식
- 수직 확장(Vertical Scaling): 서버에 CPU 및 메모리 구성 요소를 수직으로 추가함
- 수평 확장(Horizontal Scaling): 서버를 추가하여 애플리케이션의 인스턴스를 더 많이 실행하는 것

<br>

- Scaling Cluster Infra: K8s의 인프라 자체를 확장
    - Horizontal: `kubeadm join ...` 혹은 Cluster Autoscaler
    - Vertical: X
- Scaling Workloads: Pod 혹은 Node 확장
    - Horizontal: `kubectl scale ...` 혹은 Horizontal Pod Autoscaler(HPA)
    - Vertical: `kubectl edit ...` 혹은 Vertical Pod Autoscaler(VPA)

<br>

## 127. Horizontal Pod Autoscaler (HPA)

[deployment-definition.yaml](/esc/2026-01-23/deployment-definition.yaml)로 생성된 파드에서는 memory는 64Mi, cpu는 250m까지만 사용할 수 있음<br>
이때 파드의 메모리 혹은 CPU 사용량이 최대값에 근접하면 `kubectl scale deployment my-app --replicas=3`으로 수동으로 올릴 수 있음<br>
하지만 이 방식은 리소스 사용량을 지속적으로 모니터링해야 하고, 트래픽 급증에 빠르게 대응할 수 없을 수도 있음

HPA는 지속적으로 메트릭을 모니터링하다가 CPU, 메모리 또는 사용자 정의 메트릭에 따라 DeploySet이나 ReplicaSet의 파드 수를 자동으로 늘리거나 줄임<br>
또한 CPU, 메모리 사용량이 너무 높아지면 HPA는 처리 경로를 더 생성하고, 낮아지면 여분의 파드를 제거하여 리소스를 절약하고 균형을 맞춤

`kubectl autoscale deployment my-app --cpu-percent=50 --min=1 --max=10` 명령으로 Deploy를 실행하면 Metric Server릁 통해 모니터링하다가 CPU 사용량이 50%가 넘으면 복제본 수를 확장 또는 축소하도록 수정함<br>
파일로 생성한다면 [my-app-hpa.yaml](/esc/2026-01-23/my-app-hpa.yaml)처럼 작성하면 됨<br>
HPA의 상태를 보기 위해서는 `kubectl get hpa` 명령어를 확인하면 됨<br>
scale-up을 할 때 지정된 최대값을 초과하지 않으며, scale-down할 때 지정된 최소값을 초과하지 않음<br>
HPA 삭제는 `kubectl delete hpa my-app`<br>
HPA는 내부 metric server를 통해 소스에서 정보를 가져올 수 있으나, DataDog이나 dynatrace같은 클러스터 외부에 있는 소스에서 정보를 가져올 수도 있음

<br>

## 130. In-Place Resize of Pods

파드의 리소스 요구사항을 변경하는 경우, 기본적으로 기존 파드를 삭제한 다음 새 변경 사항이 포함된 파드를 스핀업함<br>
따라서 요구 사항 반영은 파드를 죽인 후 새 리소스 정의가 포함된 파드를 만듦

`FEATURE_GATES=InPlacePodVerticalScaling=true` 설정을 하면 파드 정의는 크기 조정 매개변수 집합을 지원함<br>
[deployment-in-place.yaml](/esc/2026-01-23/deployment-in-place.yaml)처럼 resizePolicy를 설정해둔 경우 리소스를 변경해도 파드를 다시 시작하지 않음<br>
따라서 컨테이너를 실제로 다시 시작하지 않고도 컨테이너에 할당된 CPU 또는 메모리 리소스의 크기를 조정할 수 있음<br>
(되게 malloc같군...)

제한 사항
- CPU 및 메모리 제한 사항에 대해서만 작동함
- Pod, Qos는 변경할 수 없음
- 초기화 컨테이너와 임시 컨테이너의 크기를 조정할 수 없음
- 리소스 요청 및 제한은 한번 설정하면 삭제할 수 없음
- 컨테이너 메모리 제한은 사용량 이하로 줄일 수 없음
- Windows 파드의 크기를 제한할 수 없음

## 131. Vertical Pod Autoscaling (VPA)

`kubectl edit deployment my-app` 명령어를 통해 resource를 조정하는 것으로 수동 조정이 가능함<br>
VPA는 HPA와 마찬가지로 지속적으로 메트릭을 모니터링한 다음 배포에서 파드에 할당한 리소스를 자동으로 늘리거나 줄여 워크로드의 균형을 유지함<br>
VPA는 기본적으로 제공되지 않으므로 배포해야 함

VPA 배포 구성 요소
- VPA Admission Controller: Recommender의 권장 사항을 사용하여 시작 시 권장 CPU 및 메모리 값을 적용하도록 파드 사양을 변경함
- VPA Updater: 최적이 아닌 리소스로 실행 중인 파드를 감지
- VPA Recommender: 리스소 사용량을 모니터링하고 파드의 과거 및 실시간 사용량 데이터를 수집한 다음 최적의 CPU 및 메모리 값에 대한 권장 사항 제공
    - 파드 직접 수정 X, 변경 사항만 제안함
- [my-app-vpa.yaml](/esc/2026-01-23/my-app-vpa.yaml)처럼 작성하면 됨
- [공식 문서](https://kubernetes.io/docs/concepts/workloads/autoscaling/vertical-pod-autoscale/)에서 mode 등 확인하면 좋음

<br>

| Feature        | VPA                                             | HPA                                          |
| -------------- | ----------------------------------------------- | -------------------------------------------- |
| Scaling Method | 개별 포드 성능 최적화                                    | 여러 인스턴스에 걸쳐 부하 분산                            |
| Pod Behavior   | 파드를 재시작하여 새 리소스 값 적용

\= 다운타임 발생                | 기존 포드를 계속 실행하고 새 포드를 간단히 스핀업

\= 지속적인 가용성 보장 |
| 트래픽 폭증         | 파드 재시작이 필요하므로 트래픽 폭증 처리 X                       | 빠른 확장이 필요한 애플리케이션에 적합                        |
| 비용 최적화         | 실제 사용량에 맞게 CPU 및 메모리 할당 조정

\= 오버 프로비저닝 방지      | 불필요한 유휴 포드 방지

\= 리소스 효율적 사용                 |
| 사용 사례          | Stateful workloads, CPU/메모리 집약적 작업(DB, ML 워크로드) | 웹/엡, 마이크로서비스, stateless services, 메시지 대기열    |
| 요약             | 개별 파드에 대한 리소스 할당 최적화                            | 수요에 따라 동적으로 파드 수 확장                          |
