## 70. DaemonSets

DaemonSets는 클러스터의 모든 노드에 항상 하나의 파드 사본이 존재하도록 함<br>
클러스터에 새 노드가 추가될 때마다 해당 노드에 파드의 복제본이 자동으로 추가되고, 노드가 제거되면 파드도 자동으로 제거됨<br>
사용 사례: 클러스터의 각 노드에 모니터링 에이전트 또는 로그 수집기를 배포하여 클러스터를 모니터링함, kube-proxy, calico 배포<br>
[daemonset](/esc/2026-01-13/daemonset.yaml)처럼 작성함<br>
Kubernetes v1.12부터는 DaemonSet이 기본 스케줄러와 NodeAffinity 규칙에 따라 노드에서 파드를 스케줄링함

## 73. Static Pods

kubelet은 노드에 로드할 파드에 대한 지침을 얻기 위해 kube-apiserver에 의존하며, 이는 etcd 데이터 저장소에 저장된 kube-scheduler의 결정에 기반함<br>
master node가 없어도 kubelet은 독립적으로 containerd가 설치된 노드를 관리할 수 있음

kubelet은 파드 세부 정보를 제공할 수 있는 apiserver이 없으므로 pod 정의 파일에 작성된 파드의 세부 정보가 필요함<br>
이는 파드에 대한 정보를 저장하도록 지정된 서버의 디렉터리에서 파드 정의 파일을 배치시키고, kubelet이 주기적으로 해당 디렉터리에서 파일을 확인해 호스트에 파드를 생성하면 됨<br>
파드 생성 뿐만 아니라 애플리케이션이 crash되거나 kubelet이 재시작을 시도하는 경우에도 파드가 계속 살아있을 수 있음<br>
apiserver나 나머지 클러스터 구성 요소의 개입 없이 kubelet이 자체적으로 생성하는 파드를 **정적 파드**라고 부름

지정된 디렉터리의 위치는 어디든 될 수 있으며, 서비스를 실행하는 동안 `--pod-manifest-path` 옵션으로 kubelet에 전달됨<br>
kubelet 서비스 파일에 직접 옵션을 지정하는 대신 `--config` 옵션을 사용하여 config 파일의 경로를 제공하고 해당 디렉터리 경로를 정적 파드 경로로 정의할 수 있음<br>
기존 클러스터를 검사하는 경우, 데릭터리 경로를 식별하기 위해 `--config` 경로를 확인함<br>
다른 쿠버네티스 클러스터(kubernetes-apiserver)이 없기 때문에 kubernetes 명령어 대신 docker ps 명령어로 파드 생성 확인 가능함

1. kubelet.service 파일에서 `--pod-manifest-path` 경로 확인
2. `--config` 옵션에서 구성 파일로 사용된 파일 확인 후 staticPodPath 확인

<br>

kubelet은 다양한 입력으로부터 파드 생성 요청을 받을 수 있음
1. 정적 파드 폴더의 파드 정의 파일 이용
2. kube-apiserver가 http API 엔드포인트를 통해 kubelet에 입력 제공

kubelet이 정적 파드를 생성할 때, 클러스터의 일부인 경우 kube-apiserver에 mirror object도 생성하므로 파드 인식을 할 수 있음<br>
다만 파드에 대한 세부 정보를 볼 수 잇지만 일반적인 파드처럼 편집하거나 삭제할 수 없음<br>
삭제하기 위해서는 노드의 manifest 폴더에서 파일을 수정해야 함<br>
파드의 이름에는 자동을 노드 이름이 추가됨

정적 파드는 컨트롤 플레인에 종속되지 않기 때문에, 정적 파드를 사용해 컨트롤 플레인 구성 요소 자체를 노드에 파드로 배포할 수 있음<br>
모든 마스터 노드에 kubelet을 설치한 다음 api, server, controller 등의 제어 영역 구성 요소의 Docker 이미지를 사용하는 포드 정의 파일을 생성함<br>
정의 파일을 지정된 manifest 폴더에 배치하면 kubelet이 제어 영역 구성 요소자체를 클러스터에 파드로 배포하는 작업을 처리함<br>
이 방식은 바이너리를 다운로드하거나 서비스를 구성할 필요가 없고, 서비스 충돌에 대해 걱정할 필요가 없음 (kubelet에 의해 자동 재시작)<br>
동일한 방식으로 kube-admin tool이 kubernetes 클러스터를 설정함

- daemonsets
    - kube-apiserver에 의해 생성
    - 클러스터의 모든 노드에서 애플리케이션의 한 인스턴스를 사용할 수 있도록 하는 데 사용
    - 사용 예제: 노드에 모니터링 에이전트 배포
- static pods
    - kubelet에 의해 생성
    - kubernetes control plane 구성 요소 자체를 배포하는 데 사용
- daemonset과 static pod 모두 kube-scheduler를 무시됨

## 76. Priority Classes

쿠버네티스는 서로 다른 우선순위를 가진 다양한 애플리케이션을 파드로 실행함<br>
priority class는 다양한 워크로드의 우선순위를 정의하여 우선순위가 높은 워크로드가 우선순위가 낮은 워크로드보다 항상 우선순위를 갖도록 함<br>
우선순위가 높은 파드를 스케줄링할 수 없는 경우, 스케줄러는 우선순위가 낮은 워크로드를 종료함<br>
예시: kubernetes components > databases > critical apps > jobs<br>
priority class는 네임스페이스가 없는 객체, 생성 후 네임스페이스의 모든 포트에서 구성 가능함

우선순위는 최고 10억에서 최저 -2억 정도의 수치로 정의할 수 있고, 숫자가 클수록 우선순위가 높음<br>
`kubectl get priorityclass`로 확인 가능함<br>
[priority-class.yaml](/esc/2026-01-13/priority-class.yaml)을 작성하고 pod.yaml에 spec: 부분에 `priorityClassName: high-priority`를 지정하면 됨<br>
해당 파드가 생성되면 우선순위 클래스에 할당된 우선순위를 가짐<br>
파드에 우선순위 클래스를 지정하지 않으면 기본값 0을 갖음.<br>
모든 파드에 우선 순위를 지정하고 싶다면 priority-class.yaml에 `globalDefault: true`를 지정하면 됨. globalDefault: true는 하나의 우선순위 클래스만 가질 수 있음<br>
우선순위 클래스에 지정된 `preemptionPolicy`가 `PreemptLowerPriority`일 경우 우선순위가 낮은 작업을 중지하고 리소스를 사용함<br>
`preemptionPolicy`가 `never`인 경우 중지하지 않고 스케줄링 큐에서 스케줄링될 때까지 기다림 (스케줄링 큐에서도 우선순위가 적용됨)
