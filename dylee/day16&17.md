# Multi-container Pods

## Microservices

- 독립적이고 작으며 재사용 가능한 코드 세트 개발, 배포 → 각 서비스 확장, 축소, 변경
- 하지만 Main App, Web Server 처럼 두 개의 서비스가 한 번에 동작해야 한다면?
    - 두 개의 인스턴스를 동시에 scale-up & scale-out 해야 함

## Multi-container Pods

- 두 개의 인스턴스는 같은 lifecycle 가짐 → 동시에 생기고, 사라짐
- 같은 network 공간 공유 → 서로 localhost로 통신 가능, Volume 공유

## Create

```yaml
apiVersion: v1
kind: Pod
metadata:
	name: simple-webapp
	labels:
		name: simple-webapp
spec:
	containers:
	#contaienr 1
	- name: web-app
		image: web-app
		ports:
			- containerPort: 8080
	#container 2 
	- name: main-app
		image: main-app
```

## Design Patterns

### 1. Co-located Containers

- 두 개의 컨테이너가 같은 공간에 존재 → 두 개의 컨테이너가 같은 Pod에 있는 것과 비슷
- 두 컨테이너 모두 Pod 전체 생명 주기 동안 계속 작동하도록 설계
- 두 서비스가 서로 의존할 때 사용
- co-located containers는 두 개의 containers의 시작 순서를 정의할 수 없음

```yaml
#Pod 생성 -> 두 컨테이너 동시에 시작
apiVersion: v1
kind: Pod
metadata:
	name: simple-webapp
	labels:
		name: simple-webapp
spec:
	containers:
	#contaienr 1
	- name: web-app
		image: web-app
		ports:
			- containerPort: 8080
	#container 2 
	- name: main-app
		image: main-app
```

### 2. Regular Init Containers

- Pod의 메인 애플리케이션 시작 전 초기화 단계에 사용 → init container 작업 수행~종료 후 main application container 시작
- 여러 개의 init container를 정의해서 사용할 수도 있음
- ex) DB가 준비될 때 까지 기다리는 init container

```yaml
apiVersion: v1
kind: Pod
metadata:
	name: simple-webapp
	labels:
		name: simple-webapp
spec:
	containers:
	#contaienr 1
	- name: web-app
		image: web-app
		ports:
			- containerPort: 8080
	initContainers:
	- name: db-checker
		image: busybox
		command: '~.sh'
```

### 3. Sidecar Containers

- sidecar container 먼저 시작 → Application container 시작
- Pod의 생명주기 동안 sidecar Container는 계속 유지됨
- log → sidecar container

```yaml
apiVersion: v1
kind: Pod
metadata:
	name: simple-webapp
	labels:
		name: simple-webapp
spec:
	containers:
	#contaienr 1
	- name: web-app
		image: web-app
		ports:
			- containerPort: 8080
	initContainers:
	- name: db-checker
		image: busybox
		command: '~.sh'
		restartPolicy: Always
```

- Always 옵션으로 메인 애플리케이션이 종료된 후 init container가 종료되도록 보장 → main container의 시작 ~ 종료 로그 catch

# InitContainers

- 각 컨테이너가 pod의 수명 주기 동안 살아있는 프로세스를 실행해야 함
    - ex) application + logging agent pods → 2개의 컨테이너가 항상 살아있어야 함 → 한개라도 실패하면 pod가 재시작
- 하지만 main web application 에서 사용할 저장소에서 코드, binary를 가져오는 작업만 완료하면 되는 프로세스, 실제 애플리케이션 구동 전 기다리는 프로세스 라면? → pod가 생성될 때 단 한번만 실행되면 됨 → initContainers를 사용하자
    
    ```yaml
    apiVersion: v1
    kind: Pod
    metadata:
      name: myapp-pod
      labels:
        app: myapp
    spec:
      containers:
      - name: myapp-container
        image: busybox:1.28
        command: ['sh', '-c', 'echo The app is running! && sleep 3600']
      initContainers:
      - name: init-myservice
        image: busybox
        command: ['sh', '-c', 'git clone <some-repository-that-will-be-used-by-application> ; done;']
    ```
    
    - pod 생성 → init Containers 실행 → initContainer process가 애플리케이션 컨테이너 시작 전에 완료 → 애플리케이션 컨테이너 실행
    
    ```yaml
    apiVersion: v1
    kind: Pod
    metadata:
      name: myapp-pod
      labels:
        app: myapp
    spec:
      containers:
      - name: myapp-container
        image: busybox:1.28
        command: ['sh', '-c', 'echo The app is running! && sleep 3600']
      initContainers:
      - name: init-myservice
        image: busybox:1.28
        command: ['sh', '-c', 'until nslookup myservice; do echo waiting for myservice; sleep 2; done;']
      - name: init-mydb
        image: busybox:1.28
        command: ['sh', '-c', 'until nslookup mydb; do echo waiting for mydb; sleep 2; done;']
    
    ```

# HPA

## Scaling

- 수직 확장 → 사용을 높이는 것
    - 기존 서버에 cpu + memory 추가
- 수평 확장 → 서버 추가해서 application의 instrance 더 많이 수행

## Scaling in k8s

- cluster 에 container + pods 추가 → workload 확장
- Scaling Workloads
    - Pod 또는 Node 확장
    - 수평 확장 → 더 많은 pod 생성
        - `kubectl scale` → deployment, statefulset, replicaset
    - 수직 확장 → 기존 pod 에 할당된 리소스 늘리기
- scaling cluster infra
    - k8ss infra 확장
    - 수평 확장 → cluster 에 더 많은 node 추가
        - `kubeadm join` → cluster에 새 node 추가
    - 수직 확장 → 기존 노드에서 resource 늘리기
        - 중단하고 다시 실행 → 권장 x

# HPA

## 한계

```yaml
# deployment-definition.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
  labels:
    app: my-app
    type: front-end
spec:
  template:
    metadata:
      name: myapp-pod
      labels:
        app: my-app
        type: front-end
    spec:
      containers:
      - name: my-app
        image: nginx
        resources:
          requests:
            memory: "64Mi"
            cpu: "250m"
  replicas: 1
  selector:
    matchLabels:
      type: front-end
```

- deployment-definition.yaml으로 생성된 pods → memory는 64Mi, cpu는 250m
    - 이걸 scale-up 하려면? → `kubectl scale deployment my-app --replicas=3`으로 수동으로 수직 확장 할 수 있음
    - 하지만 리소스 사용량을 지속적으로 모니터링해야 하고, 트래픽 급증에 빠르게 대응 x

## HPA

- 지속적으로 메트릭 모니터링
    - CPU, Memory, 사용자 정의 메트릭에 따라 DeploySet나 ReplicaSet의 Pod 수를 자동으로 늘리거나 줄임
    - CPU, 메모리 사용량이 너무 높아지면 HPA는 처리 경로를 더 생성
    - 낮아지만 Pod 제거 → 리소스 절약
- 내부 metric server을 통해 정보를 가져오거나, thrid-party service를 이용해서 정보를 가져올 수도 있다
- replicas 확장, 축소
    
    ```yaml
    apiVersion: autoscaling/v2
    kind: HorizontalPodAutoscaler
    metadata:
      name: my-app-hpa
    spec:
      scaleTargetRef:
        apiVersion: apps/v1
        kind: Deployment
        name: my-app
      minReplicas: 1
      maxReplicas: 10
      metrics:
      - type: Resource
        resource:
          name: cpu
          target:
            type: Utilization
            averageUtilization: 50
    ```
    
    - `kubectl autoscale deployment my-app --cpu-percent=50 --min=1 --max=10` 명령으로 Deploy를 실행 → 모니터링 → cpu 사용량이 50% 넘는다면 확장, 축소
- kubectl get hpa → HPA 상태 확인
- kubectl delete hpa my-app → HPA 삭제

# In-Place Resize of Pods

- pod resource 요구사항 변경 → 기존 pod 삭제 후 새 Pod 재생성
- `FEATURE_GATES=InPlacePodVerticalScaling=true`
    - 크기 조정 매개변수 집합 지원
- 컨테이너를 다시 시작하지 않고도 컨테이너에 할당된 CPU 또는 메모리 리소스의 크기를 조정하는 옵션 → resizePolicy
    - 제한 사항
        - CPU 및 메모리 제한 사항에 대해서만 작동함
        - Pod, Qos는 변경 x
        - 초기화 컨테이너와 임시 컨테이너의 크기를 조정 x
        - 리소스 요청 및 제한은 한번 설정하면 삭제 x
        - 컨테이너 메모리 제한은 사용량 이하로 줄일 수 x
        - Windows 파드의 크기를 제한 x

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
  labels:
    app: my-app
    type: front-end
spec:
  template:
    metadata:
      name: myapp-pod
      labels:
        app: my-app
        type: front-end
    spec:
      containers:
      - name: my-app
        image: nginx
        resizePolicy: #리소스를 변경해도 파드를 다시 시작 x
        - resourceName: cpu
          restartpolicy: NotRequired
        - resourceName: memory
          restartpolicy: NotRequired
        resources:
          requests:
            memory: "64Mi"
            cpu: "250m"
  replicas: 1
  selector:
    matchLabels:
      type: front-end
```

# VPA

- 지속적으로 메트릭을 모니터링 → 다음 배포에서 파드에 할당한 리소스를 자동으로 늘리거나 줄여 워크로드의 균형을 유지함
- VPA는 기본적으로 제공되지 않음 → 배포 필요
- `kubectl edit deployment my-app` → resource 수동 조정

## 구성 요소

- VPA Admission Controller
    - Recommender의 권장 사항으로 시작 시 권장 CPU 및 메모리 값을 적용하도록 파드 사양을 변경
- VPA Updater
    - 최적이 아닌 리소스로 실행 중인 파드를 감지
- VPA Recommender
    - 리스소 사용량을 모니터링하고 파드의 과거 및 실시간 사용량 데이터를 수집한 다음 최적의 CPU 및 메모리 값에 대한 권장 사항 제공
    - 파드 직접 수정 X, 변경 사항만 제안함
- 작성 방법

```yaml
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: my-app-vpa
spec:
  targetRef:
    apiVersion: "apps/v1"
    kind:       "Deployment"
    name:       "my-app"
  updatePolicy:
    updateMode: "Auto"
  resourcePolicy:
    containerPolicies:
    - containerName: "my-app"
      minAllowed:
        cpu:    "100m"
        memory: "128Mi"
      maxAllowed:
        cpu:    "1"
        memory: "512Mi"
      controlledResources: ["cpu", "memory"]
```
